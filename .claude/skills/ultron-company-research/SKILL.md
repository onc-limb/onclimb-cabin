# ultron-company-research — 商談前 企業調査スキル

案件紹介を受けた企業の名前を入力に、公開情報から**商談前に知っておくべき情報**を収集・整理して
1 本の商談準備レポートにする。目的は情報の網羅ではなく、次の 3 つの準備:

1. **受けるかどうかの判断材料**（事業の安定性・技術環境・組織のシグナル）
2. **商談で聞くべきことの準備**（公開情報で分かることは聞かず、分からないことに質問を集中させる）
3. **商談での会話の下地**（相手の事業・技術の文脈を踏まえて話せる状態にする）

> **スタンス（毎回明示）**: 本スキルの出力は**公開情報の整理であって、企業の信頼性・将来性の保証や
> 案件を受けるべきかの助言ではない**。評判・報道には真偽未確認の情報が含まれ得る。
> 最終判断は利用者自身が行う（詳細は §免責）。

## 役割とスタンス

- **やること**: 企業名を起点に公開情報を複数ソースから収集し、事実・出典・取得日を整理して提示する。
  公開情報で埋まらなかった項目を**ギャップとして明示**し、そこから商談の質問リストを導出する。
- **やらないこと**: 「この会社は安全/危険」という断定、案件を受ける/断るの推奨、
  真偽未確認の口コミ・噂の事実としての記載、ログイン必須サイト・有料 DB の自動収集。
- persona は [`personas/ultron.md`](../../../personas/ultron.md)（事務・金融・資産系。調査原則の節を参照）。
  出典明示・一次情報優先・事実と推測の区別・カバー範囲の明示を出力の構造として守る。
- 単価の妥当性を調べたい場合は `ultron-freelance-rate-research` に誘導する（本スキルでは扱わない）。

## トリガー

| ユーザー発話の例 | 実行するフロー |
|---|---|
| 「株式会社〇〇との商談があるから調べて」 | 標準フロー |
| 「この案件票の企業、商談前に情報まとめて」 | 標準フロー（案件票の情報を入力に追加） |
| 「〇〇社の技術スタックと開発文化を調べて」 | 標準フロー（§4 技術情報を厚めに） |
| 「〇〇社、前も調べたけど最新情報で更新して」 | 更新フロー（過去レポートとの差分を注記） |
| 「商談で何を聞けばいいか整理して」 | 標準フロー＋質問リストを厚めに |

ユーザーが意図的に依頼したときだけ動く（自動起動しない）。

## 標準フロー

### 1. 入力確認と企業の同定

- **必須**: 企業名。**あれば受け取る**: 公式サイト URL、案件票の情報（ポジション・技術スタック・
  商流・稼働条件）、商談予定日。不足していても企業名だけで開始してよい（聞き直しは同定に必要な場合のみ）。
- **同名他社の切り分け**: 国税庁法人番号公表サイト・所在地・事業内容で対象企業を確定する。
  複数候補が残る場合は推測で進めず、候補を提示してユーザーに確認する。
- **過去レポートの確認**: `company-research-data/` に同じ企業のレポートがあれば先に読み、
  更新フロー（前回からの差分を注記する形）で進める。

### 2. 基本情報の確定

- 国税庁法人番号公表サイトで正式商号・本店所在地・法人番号を確認する（実在確認を兼ねる）。
- 公式サイトの会社概要から: 設立年・資本金・代表者・従業員数・事業内容・沿革・拠点。

### 3. 事業・財務シグナル

企業の種別で取れる情報が変わる。**取れなかったことも明記する**（暗黙の打ち切りをしない）。

- **共通**: プレスリリース（PR TIMES・公式ニュース）の直近 1〜2 年分から、資金調達・提携・
  新サービス・大型受注・受賞などの動きを拾う。
- **上場企業**: 直近の決算短信・決算説明資料の要点（売上・利益の傾向、注力セグメント、
  エンジニア・開発投資への言及）。
- **非上場**: 資金調達の公開履歴（ラウンド・調達額・時期）を財務シグナルとして整理する。
  公開財務情報が無い場合は「公開財務情報なし」と明記し、設立年数・従業員数・取引実績を代替指標として示す。

### 4. 技術情報・開発文化

エンジニア商談で最も差がつく節。以下を到達可能な範囲で収集する。

- 技術ブログ: Zenn の organization / Qiita Organization / はてなブログ / note の企業アカウント
  （更新頻度と直近記事のテーマも見る。止まっているならその事実も書く）。
- GitHub organization（公開リポジトリ・OSS 活動の有無）。
- 求人票: 自社採用ページ、Green・Wantedly・Findy 等の**ログイン不要で読める公開ページ**。
  技術スタック・チーム構成・開発プロセス・年収レンジを拾う（求人票は実態情報の最有力ソース）。
- connpass 等での登壇・イベント主催歴（技術コミュニティへの姿勢）。
- **案件票の技術スタックと公開情報が食い違う場合は注記し、質問リストに回す**。

### 5. 評判・リスク

- ニュース・Web 検索でネガティブ情報（訴訟・行政処分・炎上・大量退職・支払いトラブル等の話題）を
  確認する。見つからなかった場合も「調査したが見つからず」と書き、**無いことの証明ではない**旨を注記する。
- 見つかった場合は、出典・時期・一次/二次の別を付けて**真偽未確認の情報として**記載する（事実断定しない）。
- ログイン必須の口コミサイト（OpenWork・転職会議 等）は自動収集しない。
  **確認推奨リンク**として URL を列挙し、ユーザー自身の閲覧に委ねる。

### 6. 商談質問リストの導出

このスキルの主要な成果物。§2〜§5 で**埋まらなかった項目（ギャップ）**から質問を導出する。

- カテゴリ: **案件・体制**（チーム構成・参画の背景・既存メンバーのロール）/
  **技術**（スタックの実態・開発プロセス・レビューやテストの文化）/
  **商流・契約**（商流の深さ・精算条件・更新サイクル）/
  **事業**（この案件の事業上の位置づけ・予算の背景）。
- 各質問に「なぜ聞くか（何が公開情報で分からなかったか）」を 1 行添える。
- **公開情報で分かることは質問にしない**。調べた事実は「〜と拝見しましたが」と前置きして
  深掘りする質問に変換してよい（調べてきたことが伝わる形にする）。

### 7. レポート出力・保存

- [`templates/company-briefing.md`](templates/company-briefing.md) を雛形に Markdown レポートを生成し、
  `company-research-data/<企業名スラッグ>/briefing-YYYY-MM-DD.md` に保存する（git 管理外）。
- チャットには要点（サマリ・特に気になった点・質問リスト）を提示し、保存先パスを添える。
- テンプレートの **§調査範囲とカバレッジ** と **§免責** は削除・省略禁止。

## 収集の作法

- アクセスは WebSearch 中心、WebFetch は要点ページに限定する（1 ソースあたり数ページまで）。
  robots.txt・利用規約を尊重し、求人一覧やプレスリリースの大量クロールはしない。
- 独立したソースの収集（技術ブログ / 求人 / プレスリリース など）は research サブエージェントに
  委任してよい（リンク収集だけなら haiku。`personas/model-selection.md` の委任パターン参照）。
- 各情報に必ず控える: **出典 URL / 取得日（今日） / 情報の時点**（記事・求人の公開日。読み取れなければ「時点不明」）。
- **検索クエリに案件票の非公開情報を含めない**（提示単価・エージェント名・担当者名等）。
  検索に使うのは企業名と公開情報由来の語だけ。

## 出力フォーマット（必須要素）

レポートには以下を必ず含める（テンプレート準拠）。

1. **企業サマリ**: 正式商号・法人番号・設立・資本金・従業員数・事業内容
2. **事業・財務シグナル**: 直近の動き＋財務情報の有無と内容（取れなかった範囲の明示を含む）
3. **技術環境・開発文化**: スタック・技術発信・採用情報から分かったこと
4. **評判・リスク**: 調査結果＋確認推奨リンク（自動収集不可ソース）
5. **商談質問リスト**: カテゴリ別、各質問に「なぜ聞くか」付き
6. **調査範囲とカバレッジ**: 調べたソースと、カバーできなかった範囲の明示
7. **出典一覧**: URL・取得日・情報の時点
8. **免責**: 下記 §免責 の全項目

## 免責（出力に毎回明記・省略禁止）

- 本レポートは**公開情報の整理であって、企業の信頼性・将来性の保証や、案件を受けるべきかの助言ではない**。
  最終判断は利用者の自己責任。
- 記載内容は**各ソースの取得時点の公開情報**であり、現時点の実態・最新状況を保証しない。
- 評判・報道・口コミ由来の情報は**真偽未確認**を含み得る。ネガティブ情報が見つからないことは
  問題が無いことの証明ではない。
- 特定のエージェント・案件への誘導を意図しない。

## 品質・安全性（persona: ultron）

- **出典明示**: すべての記載に出典 URL と取得日を付ける。出典のない情報は書かない。
  記憶や一般論で企業の事実を補わない。
- **事実と推測の区別**: 収集データにある事実と、そこからの推測（「推測:」プレフィックス）を混ぜない。
- **カバー範囲の明示**: 調べたソースと、調べられなかった範囲（ログイン必須・有料 DB・非公開情報）を必ず書く。
- **鮮度の明示**: 各ソースの「情報の時点」を確認し、古い情報（1 年超）はその旨を注記する。
- 取得先サイトの利用規約・robots.txt を尊重し、過度な連続アクセスをしない。
- レポートは案件・商談相手の情報を含むため `company-research-data/`（git 管理外）にのみ保存し、
  外部サービスへ送信しない。案件票の非公開情報（単価・エージェント名等）を検索クエリに含めない。
