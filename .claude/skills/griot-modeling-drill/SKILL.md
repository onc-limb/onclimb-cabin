# modeling-drill — モデリング練習課題（日次ドリル + 月次ドメイン課題）

モデリングのトレーニング題材を出すスキル。**日次モード**（1 日 1 問の小課題）と
**月次モード**（月 1 本の大きなドメイン課題）の 2 モードを持つ。
persona: [`personas/griot.md`](../../../personas/griot.md)（本人の力を引き出す・完成品を代わりに作らない）。

> 旧 `griot-modeling-domain-challenge`（月次）は本スキルの月次モードに統合した。
> 出力先・ファイル形式は旧スキルと互換（`challenges/monthly/`）。

## ゴール

- **日次**: 毎日 10〜30 分のモデリング思考を習慣にできる「ちょうどいい 1 問」を供給する。
- **月次**: 1 か月かけてイベントストーミング〜モデリングに取り組める
  「具体的で緊張関係のある題材」を毎月 1 本供給する。
- **課題に正解は無い**。出すのは状況・与件・問い（月次では仕様・ユーザー・制約）だけ。
  答え・誘導は出さない。
- ノート（`modeling-notes/notes/`）に積まれた気づき・教訓・未決の論点を読み、
  **類似場面（教訓が別文脈でも通用するか）と矛盾場面（教訓同士が衝突する条件）**を狙って出題する。
  出題を重ねるほど「過去の自分の結論を試す問題集」になっていく。

## 場所

- 日次の出力: `modeling-notes/challenges/daily/<YYYY-MM-DD>-<slug>.md`
  （slug は題材からの英小文字ケバブケース。例: `2026-07-23-late-fee-responsibility`）
- 月次の出力: `modeling-notes/challenges/monthly/<YYYY-MM>-<slug>.md`
  （slug はサービス形態から。例: `2026-08-equipment-rental`）
- 入力: `modeling-notes/notes/*.md`（気づき・教訓・未決の論点）、
  `challenges/daily/` と `challenges/monthly/` の過去出題（観点・題材の重複回避）。
- `modeling-notes/` は git 管理外（`.gitignore` 済み）。索引ファイルは持たない（都度走査）。
- **取り組みの記録（session-log）**: ユーザーが課題に取り組んだやり取りの記録（他ツールでの
  壁打ちログ等）は、課題ファイルの隣に `<slug>-session.md`（frontmatter に `type: session-log`）で
  置いてよい。スキルはこれを**出題として扱わない**（当日/当月ガード・過去出題の走査から除外する）。
  気づき・教訓の正本への反映は jarvis-modeling-notes 経由で行う。

## トリガー

| 発話の例 | モード / 動作 |
|---|---|
| 「今日のモデリング課題」「ドリル出して」 | 日次。当日分が無ければ生成。あれば再掲 |
| 「もう 1 問」「別の観点で」 | 日次。同日 2 問目以降を生成（ファイル名に `-2` 等） |
| 「今月のドメインに絡めたドリルにして」 | 日次。当月の月次課題の題材世界で変形出題 |
| 「今月のモデリング課題出して」「今月の題材ちょうだい」 | 月次。当月分が無ければ生成。あれば再掲 |
| 「今月の課題作り直して」「別のサービス形態で」 | 月次。作り直す（既存ファイルは `-v2` 等で残し、上書きしない） |
| 「来月の課題を先に作って」 | 月次。対象月を指定して生成 |
| 「最近のドリル一覧」「過去の課題一覧」 | 該当ディレクトリを走査して日付/月・観点/形態・狙いを表で出す |

自動起動しない。定期実行を仕込む場合はスケジュール機構側で上記の発話を発火させる
（本スキルは冪等: 当日分/当月分があれば再掲するだけ）。

## 日次モードの生成フロー

1. **当日ガード** — `challenges/daily/<今日>-*.md`（`type: session-log` は除く）が
   既にあれば再掲して終了（「もう 1 問」と言われたときだけ追加生成）。
2. **ノートと直近出題の読み込み** —
   - `notes/*.md` から教訓・未決の論点・直近の気になりを抽出する。
   - `challenges/daily/` の直近 7〜10 問を走査し、観点（下記カタログ）と題材ドメインの
     連続重複を避ける（session-log は出題として数えない。ただしノート未反映の
     気づきを把握する補助入力として読んでよい）。
   - ノートが空・薄いときは、カタログから未出題の観点を選んで一般例題として出す。
3. **観点の選定** — 小課題の観点カタログ（育てる対象）:
   - 責務配置（このロジックは誰のものか）
   - 依存の向き（汎用と特定、安定と変化）
   - 値オブジェクト vs エンティティ / 区分オブジェクト
   - 集約境界・不変条件
   - 継承 vs 委譲・インターフェース分離
   - 状態遷移・ライフサイクル
   - 時間の扱い（履歴・改定・遡及・タイムゾーン）
   - 条件分岐 vs ポリモーフィズム
   - 重複と偶然の一致（似て見えるコードを統合すべきか）
   - 双方向関連・相互参照の解消
4. **課題の生成** — 次の構成で 1 ファイル（読んで 2〜3 分・考えて 10〜30 分の分量に収める）:
   ```markdown
   ---
   date: YYYY-MM-DD
   aspect: <観点（英語 kebab-case）>
   seeds: [<狙いに使ったノートの slug>, ...]  # ノート未参照なら空
   ---

   # <題材タイトル>

   ## 状況
   <架空の業務場面。3〜6 行。特定企業を写さない>

   ## 与件
   <ルール・制約を箇条書きで 3〜6 個。数値を入れる。
    素直に置くと引っかかる緊張関係を 1 つ以上含める>

   ## 問い
   <open な問いを 1〜3 個。「どこに置くか」「どう表現するか」。答え・選択肢の誘導を書かない>

   ---

   ## 出題メモ（解いた後に読む）
   <どのノートのどの教訓・未決論点の「類似」や「矛盾」を狙ったか。[[note-slug]] で参照。
    一般例題ならどの観点の定番題材かだけ書く>
   ```
5. **通知** — 保存パスと「状況・与件・問い」を提示する（分量が小さいので全文でよい。
   ただし出題メモは見せず「末尾にあります」とだけ伝える）。
   考えた結果・気づきは jarvis-modeling-notes で記録するよう一言添える。

## 月次モードの生成フロー

1. **当月ガード** — `challenges/monthly/<YYYY-MM>-*.md`（`type: session-log` は除く）が
   既にあれば、その概要を再掲して終了
   （「作り直して」と言われたときだけ再生成。既存ファイルは残す）。
2. **ノートの読み込み** — `notes/*.md` を走査し、次を抽出する:
   - 教訓（「教訓」セクション）と、その適用条件が未検証のもの
   - 未決の論点・不明点（壁打ちエントリの「未決」、疑問形の気になり）
   - 直近 2〜3 か月でよく触れているテーマ（責務配置・依存の向き 等）
   ノートが空・薄い場合はこのステップを飛ばし、一般的な良題材として成立する課題を出す。
3. **サービス形態の選定** — 世にある一般的なサービス形態から 1 つ選ぶ
   （例: EC / 宿泊・座席予約 / サブスク / マッチング / 物流・配送 / レンタル / チケット販売 /
   フリマ / 教育・受講管理 / 会員制ジム / 医療予約 / 中古買取）。選定基準:
   - **ノートの論点と接触面が大きいこと**（類似場面・矛盾場面を自然に仕込める）
   - 過去の月次課題とサービス形態が重複しないこと（`challenges/monthly/` を走査）
   - 実在の特定企業のサービスを写さない（一般的な形態として定義する）
4. **課題の生成** — 次の構成で 1 ファイルにまとめる:
   ```markdown
   ---
   month: YYYY-MM
   service_form: <サービス形態（英語 kebab-case）>
   seeds: [<狙いに使ったノートの slug>, ...]  # ノート未参照なら空
   ---

   # <YYYY-MM> モデリングドメイン課題: <サービス名（架空）>

   ## サービス概要
   <何を提供するサービスか。3〜8 行>

   ## 想定ユーザー
   <利用者の種類と、それぞれの目的・行動。管理側・運営側も含める>

   ## 主要ユースケース
   <番号付きで 5〜10 個。イベントストーミングの入口になる粒度>

   ## 業務ルール・制約
   <料金・期限・キャンセル・在庫・権限などの具体ルール。数値を入れる。
    あえて緊張関係（素直にモデリングすると衝突する要求）を 2〜3 個含める>

   ## スコープ外
   <今回考えなくてよいこと（認証基盤・決済代行の内部 等）。課題の際限ない拡大を防ぐ>

   ## 考えどころ
   <open な問いのみ 3〜7 個。「〜はどう表現するか」「〜の責務はどこか」。
    答え・誘導・推奨は書かない>

   ---

   ## 出題メモ（解いた後に読む）
   <どのノートのどの気づき・教訓の「類似」や「矛盾」を狙ったか。[[note-slug]] で参照。
    ノート未参照の出題ならその旨>
   ```
5. **通知** — 保存パスと「サービス概要・考えどころ」を提示する。出題メモの中身は
   本文で繰り返さない（先入観を避けるため「末尾にあります」とだけ伝える）。
   気づき・不明点は jarvis-modeling-notes で随時記録するよう一言添える。

## 出題の質（類似と矛盾の仕込み方）

- 日次は **1 問 1 論点**。複数の観点を詰め込まない（大きい論点は月次の領分）。
- 与件は「どちらでも設計できるが、選ぶと何かを引き受ける」ものにする
  （一方が明らかに正しい問題は思考のトレーニングにならない）。
- **類似**: ノートの教訓が別ドメインでも成り立つかを試す場面を作る。
  教訓を試すときは**前提を 1 つだけずらす**（基準値が動的になる・区分が階層化する・
  時間で変わる 等）。全部ずらすと類似性が伝わらない。
- **矛盾**: 教訓同士・教訓と新しい制約が衝突する場面を作る
  （例: 「依存は特定→汎用の一方向」と「変更頻度の高い側に知識を寄せる」が
  素直に両立しない業務ルールを置く）。
- 仕込みは与件・業務ルールの中に**自然に**埋める。「ここが引っかけです」と本文で示さない
  （狙いは出題メモにだけ書く）。
- ノートの記述を課題本文にコピーしない（ユーザーの言葉は記録側に属する。課題は常に新しい場面）。

## 品質・安全性（persona: griot 準拠）

- **正解・模範解答・推奨設計・クラス図・コード例を出さない**。「答え合わせして」「設計の相談」は
  jarvis-modeling-notes の壁打ち（モード B）へ誘導する（そこでも結論は押し付けない）。
- 実在の特定サービス・企業の仕様を写さない。案件・顧客の情報を題材に混ぜない。
- ノート（`notes/`）は読み取り専用。書き込みは `challenges/` 配下のみ。
- 過去の課題ファイルは書き換えない（作り直しは別ファイルで残す）。
- 出力は日本語。識別子・slug は英語。

## 自己進化

固定する芯（正解を出さない・日次は 1 日 1 問 1 論点で 10〜30 分・月次は月 1 本・
ノート由来の類似/矛盾の仕込み）は崩さない。育てるのは:

- 観点カタログ（日次）とサービス形態カタログ（月次）: 出題が偏る・ネタ切れになったら追記する。
- 分量の調整: 「重すぎる / 軽すぎる」という指摘があれば、与件・ユースケース・問いの数の目安を直す。
- ずらし方・緊張関係のパターン: 効いた仕込み・空振りだった仕込みを「出題の質」節に追記する。

## やってはいけないこと

- 正解・模範解答・ヒントの誘導を出さない（問いは open に留める）。
- ノートのユーザーの言葉を課題本文に転載しない（狙いは出題メモで参照のみ）。
- 毎日・毎月の実施を催促しない・連続記録（streak）を数えて圧をかけない（空いた日・月は無かったことでよい）。
- 当日分・当月分があるのに黙って作り直さない・既存課題ファイルを上書きしない。
- `notes/` への書き込み・`projects/` 配下への保存をしない。
