# author-style — 筆者の文体ガイド（技術記事用）

friday-tech-article-drafter のドラフト生成（ステップ 3）と清書パス（ステップ 4）で適用する、
筆者本人の書きぶりの特徴。[`personas/writing-style.md`](../../../personas/writing-style.md)（AI 感の
**除去** = 引き算）と役割が異なり、こちらは筆者らしさへの**寄せ**（足し算の方向付け）を担う。
両方適用する場合は、まず本ファイルの声に寄せてから writing-style の引き算チェックを通す。

出典: Zenn 公開記事「アーキテクチャの話はなぜ伝わらないのか」
（https://zenn.dev/onclimb/articles/architecture-telling-onclimb）の文体分析と、
2026-08-03 Terraform 初期セットアップ記事でのユーザー承認済み文体（2026-08-04 拡張指示）。

## 文体ルール

| 項目 | ルール | 実例（承認済み記事より） |
|---|---|---|
| 基調 | です・ます調で統一 | — |
| 一人称 | **「筆者」**（「私」は使わない） | 「筆者も少し前までまさにその状態でした」 |
| 冒頭 | 読者への問いかけで始める。読者の状況を描写してから「〜ではないでしょうか？」 | 「開発をしていてこのような言葉を聞いたことがないでしょうか？」「そんな状態の方は意外と多いのではないでしょうか？」 |
| 結論の出し方 | 先に言い切る。「結論、〜です」の形も可 | 「結論、**アーキテクチャの話は、ハイコンテクストでは伝わらない**と割り切ることです」 |
| 節のつなぎ | 会話的な一言で橋を架ける | 「では、ようやく本題ですが」「では、始めましょう」 |
| 経験談 | 失敗・つまずきを「筆者は〜で引っかかりました」と本文に織り込む（出典にある事実のみ） | 「筆者はここで一度引っかかりました」 |
| 強調 | 記事の核となる主張・読み飛ばすと困る箇所だけ**太字**。乱用しない | — |
| 締め | 柔らかい展望で終える。「〜ていきたいですね」の形 | 「どちらも大切にしながら、より良いチーム開発を目指していきたいですね」 |
| 絵文字・記号 | 本文では使わない（Zenn の記事アイコン等メタ情報は除く） | — |

## 適用時の注意

- 文体を寄せるために**事実・体験を創作しない**（persona: friday / writing-style と同じ原則）。
  問いかけ・つなぎ・締めの「型」だけを借り、中身は出典にある事実で埋める。
- 問いかけ・「では、」の多用は逆に AI 感になる。冒頭 1 回・本題への転換 1 回程度が目安。
- 実際の公開記事が増えたら、この表の実例を差し替え・追記して育てる
  （articles/ 配下の `status: ready-to-publish` 記事が最新の正）。
